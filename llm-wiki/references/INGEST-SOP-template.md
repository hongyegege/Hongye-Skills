# Ingest 标准作业流程（SOP）

> **目的**：确保每次新文档入库时，所有必要动作一次性完整执行，不再遗漏。
> **触发场景**：用户提供新源文档（飞书文档、微信文章、网页、PDF、本地文件等）要求入库

---

## 一、Ingest 九步流程（每步必须执行）

### Step 0：去重检查（最先执行，通过则继续） ✅
```
动作：
  1. 根据文档标题/来源关键词，在知识库中搜索相似文件
     - git grep "关键词" -- *.md（如启用 Git）
     - grep -r "关键词" {知识库根目录}/ --include="*.md"（无 Git 时）
     - 查看 INDEX.md 对应分类下是否已有类似条目
  2. 判断结果：
     a. 内容完全相同 → 跳过入库，回复用户"已有相同内容"
     b. 同一文档不同版本 → 更新已有 Wiki，追加版本记录，不新建文件
     c. 内容相似但有增量 → 补充增量部分到已有 Wiki，不重复创建
     d. 全新内容 → 继续 Step 1
  3. 如果跳过了入库，log.md 记录：
     ## [日期] 跳过 | 文档标题（原因：与已有内容重复/已存在更新版本）
铁律：先查后抓，绝不盲目入库（重复入库会导致同一内容多个版本，后续维护时不知道哪个是最新的）
```

### Step 1：抓取源文档 ✅
```
输入：文档 URL / 文件路径 / 粘贴的文本
动作：根据来源类型选择适配器

  来源类型          抓取方式
  ─────────────────────────────────────────────────
  飞书文档          feishu_fetch_doc 抓取全文
  微信公众号        移动端 UA curl → 备选：搜索标题找镜像站 → web_fetch
  网页/博客         web_fetch（markdown 模式）
  本地文件          read 工具直接读取
  PDF               pdf 分析工具提取文本+图片
  粘贴文本          直接使用用户提供的原文

⚠️ 微信文章特殊处理：
  - 第一步：curl -H "User-Agent: Mozilla/5.0 (iPhone...)" 直连
  - 失败时：web_search 搜索标题 → 找到网易/知乎等镜像 → web_fetch 镜像
  - 绝不正面硬刚微信反爬（滑块验证码无法绕过）

输出：完整 Markdown 文本内容
详见 llm-wiki skill 的 references/SOURCE-ADAPTERS.md（Skill 安装目录下）
```

### Step 2：保存 Source（不可变） ✅
```
文件命名：{主题}-source.md
存放位置：{领域目录}/
内容格式：
  1. YAML 头部（source_type / source_url / fetched_at / fetched_by）
  2. 完整的原始文档正文（非摘要！）
  3. 来源链接 + 版本信息 + 抓取时间

铁律 1：source = 原始全文快照，wiki = 提炼后的结构化知识（两者分工不同，混在一起就失去了"溯源"和"编译"的双层架构意义）
铁律 2：source 必须包含可直接阅读的完整原文，禁止仅存放章节结构或大纲（只存大纲 = 信息不可逆丢失，跟没抓一样）
铁律 3：source 文件一旦创建，永不修改（它是知识的时间快照，修改后就无法追溯"当时看到的原文是什么"）
```

### Step 3：编译 Wiki 页面（可编辑） ✅
```
文件命名：{主题}.md（不带 -source 后缀）
存放位置：{领域目录}/（与 source 同目录）
内容：
  1. YAML frontmatter（title/type/category/created/updated/sources/tags/related）
  2. 一句话概述（引用块格式）
  3. 结构化正文：提炼关键信息，去掉噪音（评审记录、版本历史等）
  4. 关联页面区块（🔗）

注意：保持信息完整，不丢失关键数据
```

### Step 4：图片/资产本地化 ✅
```
存放位置：{领域目录}/ 下（与 source/wiki 同目录）
  - 单张图片 → 直接放在领域目录中
  - 多张图片 → 创建 {主题}-images/ 文件夹
下载方式：
  - 飞书文档图片 → feishu_doc_media（resource_type=media）
  - 飞书画板 → feishu_doc_media（resource_type=whiteboard）
  - 网页图片 → 提取 img URL → exec curl 下载
  - PDF 图片 → pdf 工具提取
文件命名：{序号}-{描述}.png（有意义，不随机）
Wiki 页面追加：「🖼️ 关联图片」区块，列出所有本地化图片

无图片时：跳过本步骤，记录"无图片"
```

### Step 5：更新索引与日志 ✅
```
a. log.md — 新增 Ingest 记录：
   ## [日期] Ingest | 文档标题
   - Source: 路径
   - Wiki: 路径
   - 图片: 路径（张数）
   - 来源: 原始来源 URL
   - 说明: 一句话摘要
   - INDEX: ✅ | log: ✅ | 交叉引用: ✅

b. INDEX.md — 新增条目：
   - 在对应分类表格中添加新文件行
   - 更新底部统计摘要（页面数、source 数、图片数）

   行填写示例（以产品领域为例）：
   | [网关计费方案](product/gateway-billing.md) | knowledge | 网关设备与楼宇计费系统联动的技术方案 | ✅ 1 source | ✅ 2 张 | 2026-06-14 |
   对应表头：
   | 页面 | 类型 | 摘要 | Source | 图片 | 更新日期 |

c. 交叉引用 — Wiki 页面末尾追加：
   ## 🔗 关联页面
   - [相关页面1](路径) — 简短说明关联原因
   - [相关页面2](路径) — 简短说明关联原因
```

### Step 6：完整性自检 ✅
```
对每个已创建的 source 文件执行：

  1. 检查文件大小：wc -c {source文件}
     报警阈值因来源类型而异（详见 SKILL.md 第九节阈值表）：
       - 微信/飞书文章：< 3KB → ⚠️ 报警
       - 普通网页/博客：< 1.5KB → ⚠️ 报警
       - PDF 提取文本：< 2KB → ⚠️ 报警
       - 粘贴文本：< 500B → ⚠️ 报警
     核心原则：大概率只有摘要没有原文时需要报警

  2. 检查关键内容：head -20 {source文件}
     - 确认有实际正文段落，不是只有"文章结构"或"章节列表"

  3. 批量场景额外检查：
     - 列出所有 source 文件大小：ls -la *-source.md
     - 任何低于对应来源阈值的文件 → 重新抓取补充

  4. 自检不通过 → 立即修复后再继续

铁律：不通过完整性自检的 source 文件，禁止进入 Step 7（带病的 source 会污染 Wiki 编译结果，越早发现修复成本越低）
```

### Step 7：Query 沉淀（讨论有价值的内容后执行） ✅
```
触发条件：入库过程中产生了结构化讨论（如对比分析、联动关系梳理）
存放位置：queries/ 或对应领域目录
文件命名：{主题}-query.md 或 {主题}-analysis.md
内容要素：
  - 触发场景（什么情况下会用这个 Query 模式）
  - 结构化回答/分析
  - 关键原则（从讨论中提炼的经验教训）
  - 源文档引用（关联到对应的 Wiki 页面）

铁律：有价值的讨论结束后，主动询问用户是否需要 Query 沉淀（对话中的综合分析如果不存下来，下次遇到同类问题就得重新推导）
```

### Step 8：Git Commit + Push ✅
```
1. git add {具体路径}（禁止 git add -A 操作整个工作区）
2. git status（检查：确认没有意外删除，文件数正常）
3. git commit -m "[ingest] 文档标题 + 关键信息"
4. git push（如有 pre-push hook 会自动检查）

未启用 Git 时：跳过本步骤，在 log.md 中标注"未启用版本管理"
```

## 二、自检清单（每步执行后打勾）

入库完成后，逐项确认：

- [ ] **去重检查** 已执行？（Step 0：无重复内容，或已处理增量）
- [ ] **Source** 已保存？（{领域目录}/{name}-source.md）
- [ ] **Wiki** 已编译？（{领域目录}/{name}.md）
- [ ] **图片** 已本地化？（与 source/wiki 同目录）
- [ ] **log.md** 已更新？（新增 Ingest 记录）
- [ ] **INDEX.md** 已更新？（新增条目 + 更新统计）
- [ ] **交叉引用** 已添加？（Wiki 页面末尾 🔗 关联页面）
- [ ] **完整性自检** 已通过？（Step 6：所有 source 文件达到对应来源类型阈值，见 SKILL.md 第九节）
- [ ] **Query 沉淀** 已执行？（Step 7：如有价值讨论 → queries/）
- [ ] **Git** 已 commit + push？（Step 8）

## 三、特殊情况处理

| 情况 | 处理方式 |
|------|----------|
| 内容完全相同 | 跳过入库，回复用户已有相同内容 |
| 同一文档不同版本 | 更新已有 Wiki + source 追加版本记录 |
| 内容相似但有增量 | 补充增量到已有 Wiki，不新建文件 |
| 无图片/画板 | Step 4 跳过，记录"无图片" |
| 仅查询/介绍，无新源文档 | 跳过 Step 1-6，仅执行 Step 7（Query 沉淀） |
| 外部文章（非飞书） | Step 2 仍创建 source，记录原始 URL |
| 文档特别长（>5万字） | 分段抓取，分段保存，一个 source 对应多个 Wiki |
| 来源需要登录 | 提示用户手动提供内容，或使用 browser 工具 |

## 四、批量 Ingest 协议（目录链接场景）

> **触发条件**：用户提供一个合集/目录链接，包含多篇子文章

### Phase 1 — 目录解析
```
1. 打开目录页，提取所有子文章标题 + URL
2. 列清单给用户确认（序号 + 标题 + 状态）
3. 对已有文章做去重标记（Step 0）
```

### Phase 2 — 批量抓取
```
1. 每篇文章：抓取 → 创建 source（完整原文）+ wiki（结构化）
2. 抓取方式优先级：
   a. curl 移动端 UA 直连（微信原文最稳定）
   b. web_search 标题 → 镜像站 web_fetch（备选）
   c. web_fetch 直连（普通网页）
3. ⚠️ source 文件必须包含完整原文，不是结构摘要
```

### Phase 3 — 完整性验收（关键！）
```
1. 列出所有 source 文件大小
2. 任何低于对应来源阈值的 source → 重新抓取（阈值见 SKILL.md 第九节）
3. 随机抽查 2-3 篇，确认有实际正文内容
4. 向用户汇报：文件数 / 总大小 / 验收结果

铁律：未通过验收的批次，禁止 commit + push（批量入库一旦带入问题文件，事后逐个排查的成本远大于当场验收）
```

### Phase 4 — 索引更新 + Git
```
1. 更新 INDEX.md（批量追加）
2. 更新 log.md（一条批量记录）
3. git commit -m "[batch] {合集名称} {N}篇"
4. git push
```
