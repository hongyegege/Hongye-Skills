# 需求分析与逻辑重构

输出结构以用户明确指定的模板为准；未指定时使用 `../reference/prd-template.md`。本文件只提供分析方法，不另设章节规范。

## 材料整理

- 识别目标、用户、功能、约束、数据来源和交付范围，并保留足以追溯关键规则的来源信息。
- 区分已确认事实、来源冲突、缺失信息和建议；不能从行业惯例推定用户的业务规则。
- 同一功能存在不同参数或行为时，先检查产品型号、版本、场景或角色是否不同。无法解释的差异标记为具体待确认事项，列出来源与候选值，不自行选定。

## 归并与拆分

- 按实际用户目标与功能职责归并重复描述，将交织的操作、参数、条件和异常拆开。
- 共享规则集中定义并引用；不同型号、阶段或角色的差异就地说明，不强制建立对比矩阵或附录。
- 根据材料检查是否涉及权限、模式切换、互斥、记忆、设备管理等关联。没有依据时只提出问题，不将这些能力直接加入范围。
- 例如：材料只写“支持温度调节”，则保留已知能力，将范围、步长、默认值及是否记忆等适用但未知的规则标记待确认，不填入假设数值。

## 映射到模板

- 将功能清单映射到最新模板的需求目标或概要方案，并逐项对应详细需求。
- 使用内置模板时，将各项功能映射到十字段表格；使用用户指定模板时，映射到其对应字段和章节，不强加十字段结构。复杂规则在所选模板允许的位置展开并引用。
- 流程按“触发条件 → 用户操作 → 系统响应 → 状态变化”表达，异常按“条件 → 反馈 → 状态处理 → 恢复方式”表达。
- 算法、调度、分期、图表等按需应用模板的专项指引。图表输出依据交付格式选择飞书原生画板或 Mermaid/渲染图片。

## 一致性核对

- 检查同一规则在总览、详情、公式、文案和图示中是否一致，检查上下游输入输出与状态能否衔接。
- 不把“无”“不适用”用于掩盖未知信息；不把建议当事实，不因追求完整性扩展本期范围。
- 未解决的业务冲突可以保留为清晰的待确认问题，不能同时输出互相矛盾的确定性规则。
