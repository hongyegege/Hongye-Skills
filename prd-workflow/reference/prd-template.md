# PRD 产品需求文档模板与 Agent 使用说明

> 使用方法：将本文件与本次需求材料一起提供给 Agent，并说明“请按照此模板生成 PRD”。如果暂未提供具体需求，Agent 应先询问产品/功能名称、需求背景和本次希望实现的能力。
>
> 本模板参考《家庭安全功率、时区、设备影子PRD》与《AI模式PRD》，采用四章基础结构、可选概要方案和十字段详情表，支持普通迭代及多功能、预测、调度类需求。

## 给 Agent 的使用说明

以下说明用于指导生成；最终 PRD 从“产品/功能名称 PRD”标题开始，不保留本说明区。

### 1. 结构与填写原则

- 简单需求的文档依次包含：`1. 修改历史`、`2. 需求背景`、`3. 需求目标`、`4. 详细需求`；复杂需求按下一条增加概要方案。
- 多功能之间存在重要依赖、多端协同或复杂计算链路时，在需求目标与详细需求之间增加“概要方案”；此时概要方案编号为 4，详细需求编号为 5，功能小节相应使用 5.1、5.2……。简单迭代省略概要方案，使用四章基础结构。全文编号须连续一致。
- 详细需求按功能拆分：未启用概要方案时使用 `4.1`、`4.2`……；启用时使用 `5.1`、`5.2`……。每项功能使用下方固定十字段表格，保留字段名称与顺序。
- 未使用概要方案时，“需求目标”中的每个功能项须有对应的详细需求小节。使用概要方案时，需求目标主要描述用户价值与预期结果，功能清单放在概要方案的核心功能表中，并与详细需求逐项对应；拆分子功能时说明对应关系。
- 保留原模板的简洁、直接、面向研发与测试的写作风格。根据功能复杂程度调整内容长度。
- 用户提供的信息优先；不要沿用参考文档中的功率数值、角色、行业规则或具体功能。
- 不擅自补充未确认的业务规则、参数、权限、优先级、接口或法律结论。建议方案标注“建议，待确认”。
- 缺失信息使用 `【待确认：具体问题】` 标记，并放在对应字段中；关键问题影响整体方案时，先向用户澄清。可先完成不依赖答案的部分。
- `无` 表示已明确没有该条件或流程；`不适用` 表示该字段与此功能无关；尚不清楚时使用待确认标记，不要写“无”。
- 不适用的字段仍须保留，避免遗漏检查项。不得保留未替换的 `{{占位符}}`，也不得把模板示例当作已确认事实。
- 除上述可选概要方案外，不额外增加主章节；用户明确要求时可以调整。

生成前先选择一种结构，全文只使用该结构的编号与目标格式：

| 适用情况 | 主章节顺序 | 需求目标格式 | 功能清单位置 | 详情编号 |
| --- | --- | --- | --- | --- |
| 简单迭代，无重要跨功能依赖 | 1 修改历史 → 2 需求背景 → 3 需求目标 → 4 详细需求 | 功能项/功能描述表 | 需求目标 | 4.1、4.2…… |
| 多功能依赖、多端协同或复杂计算 | 1 修改历史 → 2 需求背景 → 3 需求目标 → 4 概要方案 → 5 详细需求 | 价值与预期结果的段落/条目 | 概要方案的核心功能表 | 5.1、5.2…… |

下方正文骨架展示可选节，属于填写素材而非可原样交付的最终文档。生成时按上表调整标题、表格、目录和交叉引用，删除未选结构的说明。用户明确指定其他模板时，以用户模板为准。

### 2. 各部分写作要求

- **修改历史**：使用“版本、日期、修改人、修改内容”四列。新建默认版本为 V1.0；日期使用生成时的实际日期，修改人未知时标记待确认。
- **需求背景**：用简短段落交代当前状态、用户问题和本次迭代原因，不堆叠解决方案细节。
- **需求目标**：未启用概要方案时使用“功能项、功能描述”两列表格，汇总功能能力、用户价值和关键边界；启用概要方案时改用简短段落或条目描述价值与预期结果，功能清单放入概要方案。量化目标仅在有依据时填写。
- **概要方案（按需）**：说明整体业务链路、主要参与方、系统职责、数据流向及功能依赖，可配架构图或流程图。使用“功能、描述”两列汇总核心能力；此时需求目标改用简短段落或条目描述价值与目标，避免重复功能清单。存在多期方案时标明本期范围、后续能力及切换关系，未知内容标记待确认。
- **用户场景**：描述什么用户、在什么情境下、遇到什么问题、希望获得什么结果。存在差异时按场景 A/B/C 分开。
- **功能描述**：概括功能定位、作用对象、覆盖范围及与其他功能的关系。
- **优先级**：使用用户或团队给定的口径；未给定时标记待确认，不默认全部为高。
- **角色（用户）**：列明适用角色、可执行动作与权限限制；涉及禁用或隐藏入口时说明具体表现。
- **输入/前置条件**：说明入口路径、登录/绑定要求、设备或数据状态、必要输入等。
- **流程及规则**：作为正文重点，按“触发条件 → 用户操作 → 系统响应 → 状态变化”展开；复杂功能分组编号，简单功能使用条目。
- **输出/后置流程**：说明成功结果、数据保存、设备下发、关联更新或后续跳转。前文已经说明的内容可简要归纳，保持口径一致。
- **异常情况**：按“异常条件 → 提示/反馈 → 数据或状态处理 → 恢复方式”描述，包括适用的权限不足、无数据、离线、超时、失败等分支。
- **原型图**：在对应功能表格内放置图片或设计链接，说明页面、状态和交互。没有提供时标记待补充，不虚构图片或链接；后台功能可明确填不适用。

### 3. 规则描述与格式规范

- 明确参数的单位、范围、步长、默认值及校验时机；无关项无需强行填写。
- 明确保存/提交/生效时机，区分界面暂存、服务端保存和设备执行结果；失败回滚规则应与之对应。
- 存在条件分支时，分别写出正常路径、边界条件、重复操作、取消及回退行为。
- 涉及多端同步时，明确数据来源、同步方向、触发时机、冲突处理和重试方式；未知部分标记待确认。
- 涉及其他功能时，明确联动对象、影响范围、约束关系及更新时机。
- 界面文案应明确标题、正文、选项/勾选项和按钮；多语言仅在需求要求时提供。
- 标题使用标准 Markdown 层级：文档标题 `#`，主章节 `##`，功能小节及概要方案中的子节 `###`。
- 表格左列写字段名，右列写内容；重点条件、动作和数值使用 `**加粗**`。
- 表格内换行使用 `<br>`；复杂规则在单元格内使用“1.、2.、3.”与“•”组织层级，不依赖原生多行列表。
- 表格内的竖线须转义为 `\|`，避免破坏表格。示例中的换行、图片与链接语法应替换为实际内容。
- 原型图片使用 `![说明文字](实际图片路径或URL)`；只有设计链接时使用 `[原型/设计稿](实际URL)`。图片较多时，按操作顺序排列并注明关系。
- 原文中的蓝色编号、灰色表头、绿色高亮由具体阅读器决定；Markdown 模板用标题、表格和加粗表达层级，不以颜色承载唯一含义。

### 4. 复杂功能专项指引（按需使用）

仅在相关功能适用时，将以下内容写入既有十字段表格；不要求普通功能填写无关项。

- **开启条件与能力就绪条件**：区分用户能否开启功能、是否具备完整运行能力，以及数据不足时的过渡状态。明确补齐条件后如何进入正常状态。
- **预测与算法**：说明优化目标、输入数据来源与质量、历史窗口、预测范围、输入输出粒度、运行触发和刷新频率；明确输出对象、字段、单位及使用方。数据缺失、实测零值与真实无产出应区分处理，未知规则不自行推断。
- **效果指标**：有验收指标时写明定义、公式、样本范围、统计周期、聚合方式和阈值；检查分母为零、缺失值、极端误差等边界。涉及收益提升时明确收益口径、比较基准和评估周期。没有依据时标记待确认，不自行承诺效果。
- **调度与自动执行**：按需说明生成、校验、下发、确认、执行、更新、失效、恢复和兜底；明确各阶段的责任主体、状态变化、计划有效期、版本或新旧结果处理，以及离线重连、设备更换、计划过期时的行为。
- **约束与优先级**：区分不可突破的约束、可优化的目标及用户设置，说明冲突时谁优先、作用于哪些环节，以及不可行时的处理；相关数值引用统一来源。
- **分期与多方案**：区分本期交付、后续规划和备选方案；注明版本、适用条件、差异与切换关系。公共规则集中定义并引用，避免多个方案重复抄写后产生差异。
- **图表与时序数据**：说明实际值、预测值和计划值的来源与区分方式，时间范围、时区、粒度、刷新频率、单位、坐标轴、空值和断点处理，以及图表与列表的数据关联。计算粒度、计划粒度、展示粒度和刷新频率分别定义，不混用。
- **规则配图与复杂表格**：复杂计算图、流程图可放在相应规则附近；图片须有说明且不作为唯一规则来源。长规则、状态表或指标表难以放进单元格时，可在该功能小节下就地展开，十字段表的对应行保留摘要与明确引用，避免在 Markdown 表格中嵌套表格。

#### 飞书文档交付时的画板要求

- 最终输出为飞书文档且保留“概要方案”时，必须在该节通过飞书原生画板输出整体业务架构图，包含主要参与方、系统或功能职责、数据/业务流向及依赖关系，并附关键关系说明。
- 需要业务流程图的部分同样使用飞书原生画板，放在对应功能规则附近。流程须覆盖已确认的起点、前置校验、主路径、判断分支、异常与兜底、取消/返回和结束状态，涉及跨端时标明交互主体；未决逻辑标记待确认。
- Mermaid、SVG 等可以作为创建画板的输入，最终应呈现为文档内有内容的原生画板；代码块、静态图片、外部链接和空白画板不能替代该交付要求。长流程可拆为多个关联画板，并标明衔接关系。
- 创建及编辑遵循当前飞书文档/画板工具的实际用法，更新时复用已有画板；写入后核对引用与位置，导出预览检查节点、连线、标签、可读性及图文一致性。
- 按实际能力选择工具：相关飞书技能可用时读取其指引；技能不存在但有可用 CLI 或连接器时按工具说明完成，不能将技能文件缺失等同于画板能力不可用。需要读回引用和视觉检查能力；若内容已写入但预览不可用，标明“画板已创建，视觉校验未完成”，不能声称完成验收。
- 画板能力或权限受限时，明确列出尚未完成的图及原因；如需改用替代形式，先取得用户决定。仅输出 Markdown 文件时按适用格式提供图示，此要求不强制将本地文件发布到飞书。

#### 非飞书文档的图表要求

- Markdown 默认使用 Mermaid 围栏代码块，放在概要方案或相应功能规则附近、表格之外，保留可直接维护的图表源码。
- 整体业务架构图采用分层、分组的 `flowchart`，展示实际涉及的参与方、系统职责与数据/业务流向；业务流程默认采用自上而下的 `flowchart TD`，覆盖起止、步骤、判断、异常与兜底。跨端交互按需采用 `sequenceDiagram`，状态转换按需采用 `stateDiagram-v2`。
- 视觉上采用简洁统一配色、清晰分组和带说明的连线，突出主流程并区分异常分支；颜色不是唯一含义载体。图中节点、条件及流向与正文一致。
- 交付 Word、PDF 或阅读环境不支持 Mermaid 时，将图表渲染为 SVG 或 PNG 后嵌入，依据目标格式的兼容性选择，同时保留并交付对应 Mermaid 源文件。Markdown 可按需附图片预览。
- 渲染后检查语法、文字、连线、分支、图文一致性及页面可读性；能力受限时明确说明未完成项。用户指定其他格式或样式时优先遵循用户要求。

### 5. 输出前自检

- 四章基础结构齐全；若启用概要方案，章节与功能编号已顺延。每个功能均保留十字段表格，功能总览与详情逐项对应。
- 功能命名、角色权限、参数、边界条件、文案和原型之间无矛盾。
- 流程可操作，结果可观察，异常有处理方式，关键未决问题已明确标注。
- 概要方案、功能详情、文案、公式和原型使用相同口径；前置条件、上下游依赖与数据来源一致。
- 指标可计算且有验证口径；适用的零值、缺失、过期及失败边界有定义或待确认标记。
- 流程中已有异常或兜底时，“异常情况”字段须汇总或明确引用相应规则，不得同时填“无”；输出结果与最终状态也应一致。
- 多期、多方案的交付边界明确；共享规则无重复冲突，约束优先级与降级行为一致。
- 飞书文档中的概要业务架构图、所需业务流程图均已通过原生画板输出，画板非空、位置正确，已检查预览及图文一致性；未完成部分已明确说明。
- 非飞书文档已采用对应图表形式；需要图片的交付已检查渲染效果，并随附图表源文件。
- 删除填写指导和未使用的示例行，最终输出可直接评审的 PRD。
